 16.1 Nine days of work that cannot be merged casually
 deliberate 

 The 9 September repair set — operating controls, inventory movements including
 dual-witness destruction, operational cases and CAPA, order claim and handoff queues, the three-person
 permission matrix, Gmail API delivery, Shippo USPS with tracking, D1 backup and restore scripts, and the
 MAN/SOP drafts — is committed and pushed on save/operations-repair-2026-09-09 . Checks
 passed, type-check clean, 70 files and 628 tests green.

 Why it is still sitting there

 Pushing or merging to main automatically runs deploy-staging.yml —
 migrate and deploy. So a merge is not a merge, it is a deployment, and it should happen when someone is
 watching rather than as a side effect of tidying up.

 The migrations involved are 0041 through 0049. They are already applied to staging, so the merge
 itself is low-risk — but that is a reason to do it deliberately and verify, not a reason to do it
 absent-mindedly.

 16.2 A staging deploy reached production, and it still could
 unfixed 

 On 9 September a deploy labelled staging hit production because the generated
 configuration ignored the staging flag. Production was rolled back. No guard was added. 

 What a guard has to do

 Refuse to deploy to production unless the target is stated explicitly and matches the built configuration — not inferred, not defaulted.

 Fail loudly on a mismatch rather than picking one.

 Make the environment visible in the deploy output, so the person running it sees where it went.

 Production deploys run from a v* tag via deploy-production.yml ; that separation is right and should be the only path.

 This matters more after the cutover than before it. Today production is a worker nobody visits. The
 moment the domain points at it, an accidental deploy is a public incident.

 16.3 Staging is open, and it is serving fabricated data
 live issue 

 Confirmed on 12 September by browsing it cold with no authentication of any kind. Anyone
 with the URL reaches the full storefront.

 What is exposed

 A public lot API serving manufacturerName: "Example Peptide Manufacturing Co." , manufacturerAddress: "1 Synthesis Way, Shanghai, China" and countryOfOrigin: "China" .

 Product pages advertising four pack sizes In stock, with prices, for material not in inventory.

 A working cart and checkout.

 The real schema and the real application behaviour, indexable by anything that finds the URL.

 access.staging is already a launch-critical control with no evidence attached. This is
 what it is for. Protection also wants a noindex header, so the staging origin never competes
 with the production domain in search.

 Verified good

 /manage , /manage/lots and /manage/orders all redirect to
 sign-in when unauthenticated. The staff area is properly gated — it is the storefront that is open.

 16.4 The backup rehearsal has never finished
 incomplete 

 The scripts exist: explicit-environment D1 export, a checksum manifest, isolated restore
 verification, integrity and foreign-key checks, and a written runbook. The export failed with Cloudflare
 auth error 10000 and the rehearsal has not completed end to end since.

 What completing it means

 Export D1 and R2 for a named environment, with the checksum manifest produced.

 Restore into an isolated environment — not the source.

 Run the integrity, foreign-key and table checks and read the output.

 Record the elapsed time. A recovery objective nobody has measured is a guess.

 Have Melissa or Wisam witness the result, per the deployment-and-recovery handoff rule.

 Do it before the cutover. After the domain moves, the first time you need this will be the first time
 you find out whether it works.

 16.5 Thirty launch-critical controls, none with evidence
 seed it 

 The operating-control register is built and tested — owner, due date, evidence link,
 status, launch-critical flag, administrator review, optimistic concurrency and append-only history. Not
 one control has been populated.

 The thirty cover

 Governance and launch decision; staff access and staging protection; catalog prices and product
 files; supplier qualification and purchasing; inventory load and cycle counts; release specifications,
 representative lot, exception rule and recall rehearsal; customer eligibility; the order workflow
 rehearsal; payment, tax and month-end close; shipping origin and carriers; customer messaging and
 complaint process; backup, restore and incident rollback; counsel, insurance and facility; the hazard
 programme; and the SOP library.

 Read as a list, it is a fair summary of this entire register system — which is the point. The
 application already knows what has to be true. Nobody has told it who owns each one or attached the
 evidence.

 The rule to hold

 A control cannot be marked ready without an owner and evidence, and blocked requires a
 reason. Ammre seeds it and chases the evidence; the members approve. He owns none of the approvals,
 which is the same rule as everywhere else.

 16.6 One person can deploy
 structural 

 Nobody except Ammre can deploy, roll back, restore a backup, or diagnose an incident. The
 cutover is the worst possible moment for that to be true.

 The minimum that reduces it

 Write the deploy, rollback and restore procedures into MAN-002 at a level someone else could follow under pressure — exact commands, not a description.

 Record where every credential lives and who can obtain it, without recording the credentials themselves.

 Have a second person — a member — walk a rollback on staging once, with him watching.

 Name a fallback for the cutover window specifically, even if that is an external contractor on standby.

 This will not make anyone else competent to run the platform. It makes the difference between a bad
 week and an unrecoverable one.
