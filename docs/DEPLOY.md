# Deployment — Cloudflare Workers

The site runs as a single Cloudflare Worker built by `vinext` with
`@cloudflare/vite-plugin`. Configuration lives in `wrangler.jsonc`.

## One-time setup on a new machine

1. `npm install`
2. Authenticate wrangler, one of:
   - `npx wrangler login` (opens a browser), or
   - export `CLOUDFLARE_API_TOKEN` (token made from the **Edit Cloudflare
     Workers** template, plus D1 and R2 edit permissions).
3. If the account has more than one Cloudflare account attached, also export
   `CLOUDFLARE_ACCOUNT_ID`.
4. Copy `.dev.vars.example` to `.dev.vars` and fill in local secrets. That file
   is git-ignored and must stay so.

## Everyday commands

```bash
npm run check            # typecheck + lint + build
npm run dev              # vinext dev server with workerd bindings
npm run start            # serve the production build locally under wrangler
npm run db:generate      # write a new drizzle migration from db/schema.ts
npm run db:migrate:local # apply migrations to the local D1 used by dev/start
npm run db:migrate:staging
npm run db:migrate:prod
npm run shippo:verify   # read-only Shippo key and carrier-account check
npm run deploy:staging
npm run deploy           # production
```

Always use `npm run deploy:staging` for a staging release. Do not substitute
`npx wrangler deploy --env staging` after a vinext build: the deployable
`dist/server/wrangler.json` already contains the environment selected at build
time, so the later `--env` flag does not safely retarget it. Before and after a
manual release, verify the intended Worker name with `wrangler deployments
status --name nexphaselabs-staging`.

Migrations are plain SQL files in `drizzle/`, generated by drizzle-kit and
applied by `wrangler d1 migrations apply`. Wrangler records what it has applied
in the `d1_migrations` table of each database. Never edit an applied migration;
add a new one.

## Secrets

Secrets are never committed. Locally they live in `.dev.vars`. In Cloudflare
they are set per environment with:

```bash
npx wrangler secret put NAME
npx wrangler secret put NAME --env staging
```

`vars` in `wrangler.jsonc` are for non-secret configuration only (`APP_ENV`,
`PUBLIC_ORIGIN`).

### Shippo and USPS

Use a Shippo **test** key until rate quoting and a test-label rehearsal have
passed. Add the key only to `.dev.vars` as `SHIPPO_API_KEY`; never paste it into
chat, a ticket, source code, or `wrangler.jsonc`. Run `npm run shippo:verify` to
make a read-only carrier-account request. It reports active USPS, UPS, and FedEx
account object IDs, verifies any IDs already configured in
`SHIPPO_CARRIER_ACCOUNTS`, and does not create a shipment or purchase a label.

Local acceptance-test settings are:

```dotenv
SHIPPING_PROVIDER=shippo
SHIPPO_API_KEY=shippo_test_replace_me
SHIPPO_CARRIER_ACCOUNTS=replace_with_active_usps_object_id
SHIPPO_ORIGINS_JSON=[{"id":"primary-location","label":"Primary location","active":true,"address":{"name":"NexPhase Labs","street1":"REPLACE","city":"REPLACE","state":"CA","zip":"REPLACE","country":"US","phone":"REPLACE","email":"shipping@nexphaselabs.net","is_residential":false}}]
SHIPPING_ALLOWED_SERVICES=usps_ground_advantage,usps_priority
SHIPPING_DEFAULT_PARCEL_JSON={"length":8,"width":6,"height":4,"baseWeight":0.4,"perPackWeight":0.1}
CHECKOUT_QUOTES_REQUIRED=true
```

For staging, store the test key with `npx wrangler secret put SHIPPO_API_KEY
--env staging`. Store the named origin array privately with `npx wrangler secret
put SHIPPO_ORIGINS_JSON --env staging`; residential addresses and sender contact
details must never be placed in `wrangler.jsonc`. Up to ten locations can be
configured; each needs a stable lowercase ID, a staff-facing label, an active
flag, and a complete address. The first active location is also the default tax
origin. Add a second location to the array only after its address, contact,
residential/commercial designation, physical packing process, and carrier pickup
or tender method are approved.

The non-secret carrier account ID, approved service allowlist, and parcel profile
belong in staging `vars`. The application stores the selected origin on every
quote and label. A purchased label must be cancelled through the order Shipping
desk before the order can be cancelled. The app creates one Shippo refund request,
keeps the label blocked while the refund is pending or uncertain, and uses a
read-only refund lookup for reconciliation; staff must never press the provider
refund action again to recover an uncertain response. A replacement label is
available only after the prior refund is confirmed and the prior label is marked
voided. Every label remains in the order history.

Production requires a separate live key, explicit `LIVE_SHIPPING_ENABLED=true`,
and a witnessed live-label and refund rehearsal before launch. Test and live
Shippo data are separate, so carrier account IDs must be discovered and approved
again for production.

### Website feedback archive (optional ChatGPT retrieval)

The live website feedback channel works without an external AI credential. To let an approved ChatGPT Action search its read-only archive, set a separate random bearer token:

```bash
npx wrangler secret put CHATGPT_FEEDBACK_READ_TOKEN --env staging
npx wrangler secret put CHATGPT_FEEDBACK_READ_TOKEN
```

Use the matching environment's `/api/feedback/openapi` URL as the Action schema and configure the same token as bearer authentication. The token grants read-only access to feedback messages and optional visitor contact data, so store it as a secret and rotate it if it is disclosed. Do not reuse payment, staff-session, or deployment credentials.

### Operations digest (optional)

`DIGEST_TO` (an **admin's** address — the digest carries customer-account and staff-credential rows that only admins may see) and `DIGEST_TOKEN` (a random string of at least 32 characters, set as a secret) enable
`POST /api/digest` for an external scheduler. Any cron that can send an HTTP request works — a Cloudflare
Worker with a cron trigger, or a plain crontab:

```bash
curl -fsS -X POST https://nexphaselabs.net/api/digest -H "Authorization: Bearer $DIGEST_TOKEN"
```

Until both are set the endpoint answers 404. Admins can also email themselves the digest from the dashboard at any time.

## Automated deploys (GitHub Actions)

Three workflows in `.github/workflows/`:

| Workflow                | Trigger                                             | What it does                                                                                                                                                                                                                                      |
| ----------------------- | --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ci.yml`                | every push to a non-main branch, every pull request | typecheck, lint, tests, build                                                                                                                                                                                                                     |
| `deploy-staging.yml`    | push to `main` (or run manually)                    | checks → **build** → migrate the staging D1 → seed reference data → deploy the built worker → smoke-test `/api/health`. The build runs before the migration because a migration cannot be rolled back. Refuses to run until `STAGING_URL` is set. |
| `deploy-production.yml` | push of a `v*` tag (or run manually)                | the same against production, behind the `production` GitHub environment (add a required reviewer there to get an approval gate)                                                                                                                   |

One-time setup by the owner:

1. Create a Cloudflare API token from the **Edit Cloudflare Workers** template and add **D1:Edit** and **R2:Edit**.
2. In the GitHub repository: Settings → Secrets and variables → Actions → add secrets `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`, and the variable `STAGING_URL` (the staging worker's real origin, `https://nexphaselabs-staging.<account-subdomain>.workers.dev`, printed by the first `npm run deploy:staging`). Put the same value in `wrangler.jsonc` env.staging `PUBLIC_ORIGIN`, which ships as a placeholder; staging email links depend on it.
3. Settings → Environments → create `staging` and `production`; on `production`, add yourself as a required reviewer.
4. Worker secrets (Google Workspace mail credential or `RESEND_API_KEY`, Shippo/webhook keys, payment rails, `DIGEST_TOKEN`) are still set once with `wrangler secret put`; the workflows never touch them.
5. A brand-new production database has no products until `npm run db:seed:prod` is run once; after that the catalog is managed in the tools and the workflows only seed the reference classes.

Release: `git tag v1.0.0 && git push origin v1.0.0`. Rollback: `npx wrangler rollback` (production) or `--env staging`; migrations are additive and remain in place, which is why every migration must keep the previous worker working.

`GET /api/health` reports `{ ok, env, db }` with no caching and no data; it is what the smoke test polls.

## Rollback

Every deploy creates an immutable Worker version. To roll back:

```bash
npx wrangler versions list
npx wrangler rollback <version-id>
```

Rollback restores the previous code. It does **not** undo D1 migrations, so
schema changes are written to be backwards compatible with the previous
deploy (add columns, never rename or drop in the same release).

## Building for an environment

`@cloudflare/vite-plugin` bakes the target environment into `dist/server/wrangler.json`
at build time via the `CLOUDFLARE_ENV` variable. The `deploy:*` scripts set it
for you; a manual build is:

```bash
CLOUDFLARE_ENV=staging npm run build
npx wrangler deploy --config dist/server/wrangler.json
```

Inspect the generated configuration before a manual deploy and confirm its
Worker name is `nexphaselabs-staging`. If it is not, stop and rebuild with the
staging environment rather than adding `--env staging` to the deploy command.
